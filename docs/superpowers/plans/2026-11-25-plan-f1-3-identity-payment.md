# Plan F1.3 — identity-svc + payment-svc: khách, magic-link/Google, hồ sơ lá số khóa, lượt/thẻ, SePay (mock) + PayPal (fake)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two new Java services give the fortune platform guests, passwordless accounts (email magic-link, Google OIDC), one encrypted chart profile per account that locks after the first paid question, a credit/pass ledger, and VietQR/SePay checkout whose webhook (and 5-minute reconciliation) marks orders paid and credits the account through `PaymentSucceeded` — all runnable locally with mocked providers and no real accounts, keys or money.

**Architecture:** `identity-svc` (:8084, DB `identity`) owns guests, accounts, sessions, chart profiles and the entitlement ledger; it consumes `PaymentSucceeded` from Redpanda (idempotent on `event_id` and on `order_id`). `payment-svc` (:8085, DB `payment`) owns prices, orders, provider transactions, the "chưa khớp" queue and refund requests; it publishes `PaymentSucceeded` through the platform outbox and calls identity synchronously only to reverse credits on a refund. Both are hexagonal like `services/reading-tuvi`; providers sit behind ports (`MailerPort`, `OidcPort`, `BankTransactionsPort`, `PayPalPort`) with local fakes (Mailpit for mail, signed test webhooks for SePay, an in-process fake for PayPal). Both services are internal (called by the web BFF and reading-svc with an internal token); only `/webhooks/**` of payment-svc is meant to be public. No web UI in this plan: the spec's F1.3 scope (§9) is backend; login pages, checkout/QR screen, "chưa khớp" admin page and live balance update are F1.5b.

**Tech Stack:** Java 21, Spring Boot (parent version), JDBC + Flyway + Postgres, spring-kafka (`@KafkaListener`, `DefaultErrorHandler` + DLT), platform outbox, `RestClient`, `spring-boot-starter-mail`, `com.nimbusds:nimbus-jose-jwt` (ID-token verification; builder pins the current release), JCA AES-256-GCM / HMAC-SHA256, Testcontainers (Postgres, Redpanda), ArchUnit, JaCoCo; Mailpit (`axllent/mailpit`, MIT) as local mail catcher.

**Spec:** `docs/superpowers/specs/2026-11-24-fortune-platform-design.md` — §2 G3/G4, §5.7, §6.2 (identity), §6.5 (payment), §6.6 (calendar stored with profile), §7 (privacy), §8, §9 (F1.3 scope), §11 (guest → account merge), §12.2 (refunds), §13.2–13.3 (credits, 1 free credit, lock after first use, 1 account = 1 profile), §14.1 (packs and prices), "Thanh toán SePay — cách cộng lượt", §15 (18+ confirmation, refund policy, transaction history). Platform rules: `CLAUDE.md`, `.claude/skills/java-service-conventions/SKILL.md`. Patterns to copy: `services/reading-tuvi` (pom, Dockerfile, exception handler, ArchUnit, ContractTest), `services/order-svc` (outbox adapter, `OrderFlowIT` with Redpanda).

## Review Focus

1. **Same SePay transaction delivered twice** (webhook retry, or webhook + reconciliation, or two replicas) → one `provider_transaction`, one `PAID`, one `PaymentSucceeded`; identity also ignores a second event for the same `order_id` with a different `event_id`. Tests in Task 7 (`duplicate_webhook_is_a_noop`, `reconcile_after_webhook_is_a_noop`) and Task 5 (`same_order_new_event_id_grants_once`).
2. **Real-world transfer content** — lowercase code, code glued to bank text (`TV8K2QABFT25330…`), two candidate codes, no code, underpaid, overpaid, payment arriving after the 30-minute window, payment to an already-paid order → lowercase/glued/late match; overpaid → `PAID` + note; others → "chưa khớp" with `reason` `NO_CODE|AMBIGUOUS|AMOUNT_LOW|ALREADY_PAID|UNKNOWN_CODE`, still HTTP 200 to SePay. Tests in Task 7 (`OrderCodeMatcherTest`, `SepayWebhookIT`).
3. **Two concurrent consumes for the last credit** (double click, two tabs) → exactly one 200, the other 409 `reason=no_credits`; balance never negative. Test in Task 5 (`concurrent_consume_of_last_credit`).
4. **Magic link misuse** — unknown vs known email, 4th request within 15 minutes, reused token, expired token, mail scanner GET → `POST /auth/magic-links` is always 202 with the same body (no account enumeration, rate-limited requests send no mail); verify is POST-only, single use, 15-minute TTL → second use 401. Tests in Task 2.
5. **Secrets/PII in logs** — a full login + profile + webhook run must not print the email, any token, the birth string, the transfer content or the account number. Test `NoPiiInLogsIT` in Task 5 (identity) and Task 7 (payment), capturing stdout via `OutputCaptureExtension`.
